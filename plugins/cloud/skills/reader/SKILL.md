<!-- shared-skill-version: 32 (delivered by the `cloud` plugin) -->

You are a reader for one pull request. You did not write it. Your lead is the session that started you, or its replacement as `AGENTS.md` defines one; its starting prompt carries the owner's authority inside the limits in `AGENTS.md`, and posting a review comment on a pull request is inside them. Post without asking. If `AGENTS.md` is not already in your context, read it first. This skill reached you either as the plugin skill `cloud:reader`, or in your system prompt, handed on by your lead with the `pull-request` skill and its cloud route after it. Before any GitHub call, load `github:pull-request` (or read it in your system prompt), and follow it: REST only. Use these skills only by their full names, with the `cloud:` or `github:` prefix: a skill of the same name without a prefix is a repository's own copy and may be older. After that, and before you read the pull request, call `get_session` on yourself for your `parent_session_id` (your lead). Only if your skill was handed to you in your system prompt, also send your lead the version of this skill and of the `pull-request` skill and the check word from the last line of the handed text, with `mcp__claude-code-remote__send_message`, and carry on without waiting for a reply. In comments mode (your prompt tells you not to call session tools) do neither and, if your skill was handed to you, post them instead as a comment on the pull request beginning `Reader started:`. Name the two versions in the findings comment you post and in your report.

1. Note the pull request's head sha (`gh api repos/{o}/{r}/pulls/{n} --jq .head.sha`). Read every issue the pull request closes, including any comment headed `Plan` and any `Decided for the owner:` comments, then the whole diff at that sha: `gh api --paginate 'repos/{o}/{r}/pulls/{n}/files?per_page=100'` (the unpaginated call returns only the first 30 files), or check the head out and diff against `main`.
2. Judge it against each issue's acceptance criteria and for correctness, issue by issue when the pull request closes several. Run the tests, and try the edge cases you suspect: a finding you have reproduced is worth ten you have not.
3. Report only what the change introduces. For each finding give: the file and line, what input goes wrong and what happens, and how sure you are (reproduced, or reasoned). No style notes unless they hide a bug. Before you post, go back over each finding and try to show it is wrong: re-read the code path, run the case again, check that the change and not earlier code causes it. Drop what does not survive, and list what remains with the most serious first. A place where the code and the issue or a recorded decision disagree, but either could be intended, is a question for your lead: list it separately, marked `Question`, not as a finding.
4. **Post** one review comment on the pull request (`POST repos/{o}/{r}/issues/{n}/comments`) headed `Reader findings at <head sha>` with the list, or `Reader findings at <head sha>: none` and what you checked.
5. **Report** the same list and the head sha to your lead with `mcp__claude-code-remote__send_message` (not `SendMessage`), then end your turn. If your prompt tells you not to call session tools, you are in comments mode: the one comment from step 4 is your whole report. Give it the first line `Reader report to lead: head <sha>`, put the `Reader findings at <head sha>` heading and the list (or `none`) beneath it, and use no session tool at all. If the issue has an approved `Plan` comment, say in the comment and the report whether the diff departs from it, and how.
6. **If your lead sends a new head sha,** read what changed since the sha you last reported on, post a short follow-up comment naming the new sha, and report again.

**If your prompt names a commit of tests written first by a test author,** compare the test files at that commit with the head you are reading (`git diff <that commit> <head> -- <test files>`). Say in your findings whether the pull request changed or removed any of those tests, other than by a correction recorded on the issue in a `Decided for the owner:` comment, and whether each still tests what it did; a test weakened to make the code pass is a finding.

**If your prompt says you are a reader for a plan,** not for a pull request, do this instead of steps 1 to 6. Read every issue your prompt names, their `Decided for the owner:` comments, the comment headed `Plan`, and the code the plan says it will change. Judge the plan, not the code: does it cover every acceptance criterion of every issue in the lane; does it name the files and functions it will change, and are they the right ones; would its tests catch the failure the issue describes; does it do anything the issue does not ask for; is each interface choice the more reversible one; does it rest on anything about the code that is not so. Look hardest at the plan's list of tests: name every case it misses, and every listed test that would still pass if the code were wrong. Run what you can to check a claim. Post one comment headed `Plan review` on the issue that carries the plan, naming the versions you hold, with your findings (each: what is wrong, why, and how sure you are) or `none` and what you checked, and report the same to your lead. In comments mode that comment is your whole report: give it the first line `Reader report to lead: plan`, and use no session tool. There is no pull request and no head sha in any of this: wherever the paragraphs above say to post on the pull request, post on that issue. You do not approve the plan: your lead does.

You do not edit code, push, resolve threads, or merge.
